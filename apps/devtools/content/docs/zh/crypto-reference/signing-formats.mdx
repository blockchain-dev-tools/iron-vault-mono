# 签名格式

OldPhone Wallet 在两条链上实现了四种签名操作。所有签名逻辑位于 `packages/crypto/src/signer.ts`。

每个函数返回原始字节数组，而非十六进制字符串。APDU 层负责将签名结果编码为 Ledger 响应帧。

---

## 输出格式

所有以太坊签名函数均返回 65 字节的缓冲区，布局如下：

```
[ v (1 字节) | r (32 字节) | s (32 字节) ]
```

`v` 值编码了恢复位，对于传统交易还包含链 ID 信息。具体数值因签名方法而异——详见各小节中的表格。

Solana 签名返回 64 字节的原始 Ed25519 签名，无额外封装。

---

## ETH：交易签名

**函数：** `signEthTransaction(privKey, rlp)`

```ts
function signEthTransaction(privKey: Uint8Array, rlp: Uint8Array): Uint8Array
// 返回：v(1B) + r(32B) + s(32B) = 65 字节
```

### 算法

```
hash = keccak256(rlp)
sig  = secp256k1.sign(hash, privKey, { lowS: true })
```

输入 `rlp` 是宿主应用传来的完整原始交易字节——对于 EIP-2718 类型交易，包含类型前缀字节。哈希对完整字节序列做单次计算，不进行二次哈希。

`lowS: true` 确保签名的 `s` 分量始终落在曲线阶的下半区间，这是 EIP-2 的要求，也是所有现代以太坊客户端所期望的。

### v 值计算

`v` 值因交易类型而异。OldPhone Wallet 通过检查 `rlp` 的第一个字节来区分类型化交易与传统交易：

| 交易类型 | 判断条件 | `v` 值 |
|---|---|---|
| EIP-1559（type 2） | `rlp[0] === 0x02` | 恢复位（0 或 1） |
| EIP-2930（type 1） | `rlp[0] === 0x01` | 恢复位（0 或 1） |
| 传统 EIP-155 | `rlp[0] > 0x7F` | `37 + recovery`（链 ID = 1，硬编码） |

代码实现使用单一条件判断：

```ts
const isTyped = rlp[0] <= 0x7f;
const v = isTyped ? recoveryBit : 37 + recoveryBit;
```

EIP-2718 类型化交易（type 1 和 type 2）将链 ID 直接编码在 RLP 载荷中，因此 `v` 仅携带恢复位。传统 EIP-155 交易按公式 `v = 2 * chainId + 35 + recovery` 将链 ID 编入 `v`；当 `chainId = 1` 时化简为 `37 + recovery`。

> **注意：** 传统交易的链 ID 目前硬编码为 `1`（以太坊主网）。类型化交易不受影响，因为链 ID 已嵌入其 RLP 载荷。

## ETH：个人消息签名

**函数：** `signEthPersonalMessage(privKey, message)`

```ts
function signEthPersonalMessage(privKey: Uint8Array, message: Uint8Array): Uint8Array
// 返回：v(1B) + r(32B) + s(32B) = 65 字节
```

### 算法

实现 [EIP-191](https://eips.ethereum.org/EIPS/eip-191) `personal_sign`：

```
prefix  = "\x19Ethereum Signed Message:\n" + len(message)
payload = prefix || message
hash    = keccak256(payload)
```

其中 `len` 是 `message.length`（字节数）的十进制字符串表示——不是十六进制，也不是填充整数。

```ts
const prefix = new TextEncoder().encode(
  `\x19Ethereum Signed Message:\n${message.length}`
);
```

### v 值

```
v = 27 + recovery
```

`personal_sign` 的 `v` 始终为 `27` 或 `28`，与链 ID 无关。这是早于 EIP-155 的历史惯例，也是所有以太坊钱包和 DApp 对此签名方式的统一期望。

## ETH：EIP-712 结构化数据签名

**函数：** `signEthEip712(privKey, domainHash, structHash)`

```ts
function signEthEip712(
  privKey: Uint8Array,
  domainHash: Uint8Array,  // 32 字节
  structHash: Uint8Array,  // 32 字节
): Uint8Array
// 返回：v(1B) + r(32B) + s(32B) = 65 字节
```

### 算法

实现 [EIP-712](https://eips.ethereum.org/EIPS/eip-712) 哈希模式：

```
payload = 0x19 || 0x01 || domainHash(32B) || structHash(32B)
          = 共 66 字节
hash    = keccak256(payload)
```

```ts
const payload = new Uint8Array(2 + 32 + 32);
payload[0] = 0x19;
payload[1] = 0x01;
payload.set(domainHash, 2);
payload.set(structHash, 34);
const hash = keccak_256(payload);
```

两字节前缀 `\x19\x01` 是 EIP-712 的版本标识符。该函数工作在**哈希模式**：它不自行计算 `domainHash` 或 `structHash`，而是直接接收调用方预先计算好的 32 字节值。宿主应用（OKX Wallet、MetaMask 等）需从结构化数据中计算出这两个哈希，再通过 APDU 载荷传入本函数。

### v 值

```
v = 27 + recovery
```

与 `personal_sign` 相同，始终为 `27` 或 `28`。

## SOL：消息签名

**函数：** `signSolanaMessage(privKey, message)`

```ts
function signSolanaMessage(privKey: Uint8Array, message: Uint8Array): Uint8Array
// 返回：64 字节原始 Ed25519 签名
```

### 算法

```ts
return ed25519.sign(message, privKey);
```

Solana 签名是直接的 Ed25519 签名操作，无前缀，无预哈希。Ed25519 算法内部按 RFC 8032 的规定将 SHA-512 作为其计算的一部分，但这对调用方是透明的。

`message` 参数是 Solana SDK 生成的序列化交易消息——通常是 `VersionedTransaction` 或传统 `Transaction` 序列化后的字节流，不附加任何额外封装。

输出是符合 Ed25519 规范的 64 字节签名，格式为 `(R, S)`。没有 `v` 字节。

---

## 汇总对比

| 方法 | 输入 | 哈希构造 | `v` 值 | 输出大小 |
|---|---|---|---|---|
| `signEthTransaction` | RLP 字节 | `keccak256(rlp)` | `0/1`（类型化）或 `37/38`（传统） | 65 字节 |
| `signEthPersonalMessage` | 原始消息 | `keccak256("\x19Ethereum…\n{len}" \|\| msg)` | `27/28` | 65 字节 |
| `signEthEip712` | domainHash + structHash | `keccak256("\x19\x01" \|\| domain \|\| struct)` | `27/28` | 65 字节 |
| `signSolanaMessage` | 序列化交易 | 无（Ed25519 内部使用 SHA-512） | 无 | 64 字节 |

---

## Low-S 规范化

三个以太坊签名函数均向 `secp256k1.sign` 传入 `{ lowS: true }`。这指示 `@noble/curves` 库在 `s` 落入 secp256k1 阶的上半区间（`s > n/2`）时对其取反，产生一个 `s` 值更小的等效签名。

Low-S 签名是 EIP-2 的要求，自 Homestead 版本起由以太坊客户端强制执行。若不启用此选项，部分签名将被链上 `ecrecover` 拒绝。

---

## 错误处理

签名函数均不校验私钥的长度或格式。若传入非 32 字节的密钥，底层 `@noble/curves` 原语将产生未定义行为。密钥校验由派生层（`deriveEthPrivateKey`、`deriveSolanaPrivateKey`）负责——这两个函数始终返回恰好 32 字节的密钥。
