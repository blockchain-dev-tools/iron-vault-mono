## 命令格式

OldPhone Wallet 实现的是 Ledger 方言的 APDU 协议，遵循 ISO 7816-4 标准：

```
请求：  CLA  INS  P1  P2  Lc  [Data...]
响应：  [Data...]  SW1  SW2
```

| 字段 | 长度 | 说明 |
|---|---|---|
| `CLA` | 1 字节 | 类字节——标识所属 App 或层级 |
| `INS` | 1 字节 | 指令字节——具体命令 |
| `P1` / `P2` | 各 1 字节 | 参数字节（含义由命令决定） |
| `Lc` | 1 字节 | `Data` 的字节数（无数据时为 0） |
| `Data` | 0–255 字节 | 命令载荷 |
| `SW1 SW2` | 2 字节 | 响应状态字（`9000` 表示成功） |

命令和响应通过 BLE 以 Ledger 帧格式传输（TAG + 分片序号 + 总长度）。APDU 层不感知 BLE 帧头——传输层在派发前已将其剥离。

## CLA 路由表

`@ble-vault/apdu` 中的 APDU 派发器在进入任何 App 具体处理器之前，先按 `CLA` 字节进行路由：

| CLA | 路由目标 |
|---|---|
| `0xB0` | OS 层——`GET_APP_AND_VERSION` |
| `0xE0` | 先经 OS 层（`GET_VERSION`、`OPEN_APP`、`QUIT_APP`、`GET_DEVICE_INFO`），再按 `currentApp` 派发至以太坊或 Solana 处理器 |
| `0xE1` / `0xF8` | Bitcoin New App 处理器 |
| `0x14` | Tron App 处理器 |
| `0x07` | Sui App 处理器 |

当 `CLA = 0xE0` 且没有 OS 命令匹配时，继续派发至以太坊处理器（默认）或 Solana 处理器，取决于最近一次 `OPEN_APP` 命令设置的 `currentApp` 值。

## App 切换

`OPEN_APP` 和 `QUIT_APP` 控制哪个 App 级处理器接收 `CLA 0xE0` 命令：

**OPEN_APP — `E0 D8 00 00 Lc [AppName]`**

将 `currentApp` 切换为 `Data` 中的 UTF-8 App 名称。例如，激活 Solana 处理器：

```
E0 D8 00 00 07 536F6C616E61
                └──────────── "Solana" 的 ASCII 编码
```

常用 App 名称：`Ethereum`、`Solana`、`Bitcoin`。

**QUIT_APP — `E0 A7 00 00 00`**

将 `currentApp` 重置为 `'BOLOS'`（OS 主界面）。此后 `CLA 0xE0` 命令默认进入以太坊处理器。

两条命令均只响应 `9000`。

## OS 层命令

以下命令在 App 路由之前处理，与 `currentApp` 无关：

| 命令 | APDU | 说明 |
|---|---|---|
| `GET_VERSION` | `E0 01 00 00 00` | 返回 target ID、SE 版本 `2.1.0`、MCU 版本 `1.13` |
| `GET_APP_AND_VERSION` | `B0 01 00 00 00` | 返回当前 App 名称和版本 |
| `GET_DEVICE_INFO` | `E0 E2 00 00 00` | 返回硬件版本、语言、入门状态 |

`GET_APP_AND_VERSION` 响应格式：
```
01 + name_len(1) + name(n) + ver_len(1) + ver(m) + flags_len(1) + flags(1) + 9000
```

以太坊 App 激活时的示例：
```
format=01  name="Ethereum"  ver="1.10.3"  flags=02
```

## 状态字

每条 APDU 响应都以 2 字节状态字结尾：

| 状态字 | 十六进制 | 含义 |
|---|---|---|
| 成功 | `9000` | 命令执行成功 |
| INS 不支持 | `6D00` | 该 CLA/App 下的未知指令 |
| P1/P2 无效 | `6B00` | 参数字节超出范围 |
| 数据长度错误 | `6700` | `Lc` 或载荷长度不正确 |
| 内部错误 | `6F00` | 处理器中发生意外异常 |
| 用户拒绝 | `6985` | 用户在确认页面拒绝了签名请求 |
| 继续（BTC） | `61XX` | 多帧响应，后续还有数据 |

## 延迟签名模型

签名命令（`SIGN_ETH_TRANSACTION`、`SIGN_PERSONAL_MESSAGE`、`SIGN_EIP_712`、Solana 的 `SIGN_TRANSACTION`）不会立即完成签名，而是：

1. 累积所有数据帧，直到完整载荷接收完毕。
2. 调用由 UI 层通过 `setSignRequestHandler` 注册的回调 `signRequestHandler`。
3. 挂起等待回调 resolve。
4. 批准时返回签名字节，拒绝时返回 `6985`。

UI 导航至确认页面，展示解码后的交易详情，用户点击批准或拒绝后，Promise resolve。

**签名会话超时：** 120 秒。若用户在此窗口内未操作，处理器自动以 `6985` resolve。

```ts
// 注册处理器（apps/mobile）
setSignRequestHandler(async (req: SignRequestData) => {
  return new Promise(resolve => {
    showConfirmScreen(req, {
      onApprove: () => resolve('sign'),
      onReject:  () => resolve('6985'),
    });
  });
});
```

`reject` 回调始终以字符串 `'6985'` resolve，而非调用 `Promise.reject()`——APDU 处理器始终收到干净的状态字响应。

## 多帧交易

当交易超过 BLE MTU 时，宿主将其拆分为多个 APDU 帧：

- **第一帧**（以太坊 `P1 = 0x00`，Solana `P1 = 0x01`）：包含 BIP-32 路径和载荷开头部分。
- **续帧**（以太坊 `P1 = 0x80`，Solana `P1 = 0x00`）：携带剩余载荷字节。

处理器在内存中累积分片，直到达到预期总长度（以太坊从 RLP 信封推断，Solana 从 `P2` 标志位推断），再一次性完成签名。
