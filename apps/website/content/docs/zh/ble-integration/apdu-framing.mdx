## 概述

BLE 每包有效载荷受 ATT MTU 硬性限制。一条 APDU 命令可能超过单个 BLE 包的容量，因此 Ledger 传输层在发送前会对 APDU 进行分帧封装：每帧携带一个标签字节、一个分片序号，以及（仅首帧）完整 APDU 的总长度。接收方累积分片，直到收齐 `totalLength` 字节后，将重组好的 APDU 交给应用层处理。

IRON Vault 在接收路径（宿主 → 设备，经由 Write/WriteCmd 特征）和发送路径（设备 → 宿主，经由 Notify 特征）上均实现了此分帧协议。

---

## 协议标签

共定义两个标签值：

| 标签 | 十六进制 | 用途 |
|------|---------|------|
| `TAG_MTU` | `0x08` | MTU 协商帧 — 5 字节请求/响应 |
| `TAG_APDU` | `0x05` | APDU 数据帧 — 承载命令或响应载荷 |

所有帧以其中一个标签字节开头。标签未知的帧将被静默丢弃。

---

## 首帧字节布局

首帧（分片序号为 0）在字节 3–4 携带 APDU 总长度，接收方据此在后续分片到达前申请精确大小的重组缓冲区。

| 字节 | 字段 | 值 / 说明 |
|------|------|----------|
| 0 | 标签 | `0x05`（TAG_APDU） |
| 1–2 | 分片序号（BE uint16） | `0x00 0x00` — 首帧固定为零 |
| 3–4 | APDU 总长度（BE uint16） | 例如 5 字节 APDU → `0x00 0x05` |
| 5… | APDU 数据 | 最多 `MTU − 5` 字节的 APDU 载荷 |

默认 MTU 有效载荷为 20 字节时，首帧最多携带 15 字节 APDU 数据（`20 − 5 字节帧头`）。

---

## 后续帧字节布局

首帧之后的分片省略总长度字段（已在第 0 帧中传达），帧头缩短 2 字节，每帧可携带更多 APDU 数据。

| 字节 | 字段 | 值 / 说明 |
|------|------|----------|
| 0 | 标签 | `0x05`（TAG_APDU） |
| 1–2 | 分片序号（BE uint16） | `0x00 0x01`、`0x00 0x02`… 依次递增 |
| 3… | APDU 数据 | 最多 `MTU − 3` 字节的 APDU 载荷 |

MTU 有效载荷 20 字节时，后续帧最多携带 17 字节 APDU 数据（`20 − 3 字节帧头`）。

---

## 重组算法

接收方为每条连接维护一个小型状态机：

```
状态变量：
  expectedChunkIdx  = 0
  totalLength       = 0   （从第 0 帧字节 3–4 读取）
  apduBuffer        = []
  apduReceived      = 0

收到帧时：
  tag      = frame[0]
  chunkIdx = uint16_BE(frame[1], frame[2])

  if tag != TAG_APDU:
    处理 TAG_MTU 或丢弃
    return

  if chunkIdx != expectedChunkIdx:
    // 乱序帧 — 丢弃整条消息，重置状态
    reset()
    return

  if chunkIdx == 0:
    totalLength  = uint16_BE(frame[3], frame[4])
    apduBuffer  += frame[5:]
    apduReceived = len(frame) - 5
  else:
    apduBuffer  += frame[3:]
    apduReceived += len(frame) - 3

  expectedChunkIdx += 1

  if apduReceived >= totalLength:
    dispatch(apduBuffer[:totalLength])
    reset()
```

关键不变量：
- `totalLength` 只从首帧（分片序号 0）读取。
- 任意一帧乱序到达（`chunkIdx != expectedChunkIdx`），整条 APDU 被丢弃，状态归零。协议不支持选择重传或重发 — BLE GATT 链路层保证有序交付，乱序到达意味着分帧错误。
- `dispatch` 时将 `apduBuffer` 截断到 `totalLength`，防御超长末帧。

## 响应帧格式

设备响应使用**完全相同的帧布局**，方向相反 — 通过 Notify 特征的 `notifyCharacteristicChanged()` 推送。响应 APDU 的分片与索引方式与请求完全一致，宿主用同一算法重组。

示例：MTU 20 时，67 字节的 ETH 签名响应（`v(1) + r(32) + s(32) + 9000(2)`）拆分为四帧通知：

| 帧编号 | 发送字节 | 内容 |
|--------|---------|------|
| 0 | `05 00 00 00 43 <15 字节>` | 帧头 + 响应前 15 字节 |
| 1 | `05 00 01 <17 字节>` | 后续 17 字节 |
| 2 | `05 00 02 <17 字节>` | 后续 17 字节 |
| 3 | `05 00 03 <18 字节>` | 最后 18 字节 |

`0x0043` = 67（首帧帧头中的 APDU 总长度）。

---

## 帧间延迟

Android 实现在连续的 `notifyCharacteristicChanged()` 调用之间插入 **20 ms 休眠**。部分宿主 BLE 协议栈在通知帧到达速度超过连接间隔时会丢弃数据。20 ms 延迟保守但安全 — 帧吞吐约为 50 帧/秒，对所有钱包 APDU 场景均已足够。

## MTU 协商帧

`TAG_MTU`（`0x08`）帧是仅在连接握手阶段（第 5 步）使用的特殊 5 字节消息，不携带 APDU 载荷。

| 方向 | 帧字节 | 含义 |
|------|--------|------|
| 宿主 → 设备 | `08 00 00 00 00` | 查询设备 MTU |
| 设备 → 宿主 | `08 00 00 00 00 14` | MTU 有效载荷为 20（0x14）字节 |

设备响应的第 6 个字节为 MTU 有效载荷大小，`0x14` = 20。双方随后以此值计算所有后续 APDU 帧的分片大小。

---

## 具体示例

**在 MTU 有效载荷 = 20 的情况下发送 `E0 01 00 00 00`（GET_VERSION，5 字节）：**

APDU 完整地放入首帧。总长度 = `0x0005`，APDU 数据占字节 5–9。

```
字节:  00  01  02  03  04  05  06  07  08  09
值:    05  00  00  00  05  E0  01  00  00  00
       ^^  ^^^^^  ^^^^^  ^^^^^^^^^^^^^^^^^^^
      标签  序号=0  长度=5       APDU 载荷
```

单帧传输 — 无需后续分片。

**在 MTU 有效载荷 = 20 的情况下发送 22 字节 APDU：**

首帧（字节 0–19）：
```
05 00 00 00 16 <APDU 前 15 字节>
```
`0x0016` = 22，携带 APDU 前 15 字节。

第二帧（剩余 7 字节）：
```
05 00 01 <APDU 后 7 字节>
```
两帧合计传输字节数：20 + 10 = 30。
