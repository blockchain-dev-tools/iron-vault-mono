## 激活方式

宿主发送 `OPEN_APP "Solana"` 后，Solana 处理器接管 `CLA 0xE0`：

```
E0 D8 00 00 07 536F6C616E61
                └──────────── "Solana" 的 ASCII 编码（7 字节）
```

此后所有 `CLA 0xE0` 命令都路由至 Solana 处理器，直到收到 `QUIT_APP`（`E0 A7`）或新的 `OPEN_APP`。

**密钥派生方案：** SLIP-10 Ed25519，HMAC-SHA512 主密钥字符串为 `"ed25519 seed"`。每个路径分量**必须**为硬化派生（最高位置 1）。Ed25519 不支持非硬化派生，使用非硬化分量将产生错误的密钥。

## GET_APP_CONFIGURATION — INS 0x01

返回 Solana App 版本号和功能标志。

**完整 APDU：** `E0 01 00 00 00`

**响应格式：**
```
blind_sign_enabled(1)  +  major(1)  +  minor(1)  +  patch(1)  +  9000
```

**固定响应：** `01 01 03 00 9000` = 盲签名已启用，版本 1.3.0。

---

## GET_PUBKEY — INS 0x05

从 SLIP-10 BIP-32 路径派生 32 字节 Ed25519 公钥。

**完整 APDU：** `E0 05 00 00 Lc [BIP32Path]`

**请求数据格式：**
```
path_count(1)  +  [path_component(4) × path_count]
```

所有路径分量必须设置硬化位（`| 0x80000000`）。Solana 标准派生路径为 `m/44'/501'/0'/0'`。

**响应格式：**
```
pubkey(32)  +  9000   共 34 字节
```

---

## GET_ADDRESS — INS 0x07

派生公钥，并以 base58 编码字符串形式返回 Solana 地址。

**完整 APDU：** `E0 07 00 00 Lc [BIP32Path]`

**请求数据格式：** 与 `GET_PUBKEY` 相同。

**响应格式：**
```
addr_len(1)  +  addr_bytes(n, base58 字符串)  +  9000
```

地址是 32 字节 Ed25519 公钥的 base58 编码——即标准 Solana 链上地址格式。

## SIGN_MESSAGE — INS 0x04

## SIGN_TRANSACTION — INS 0x06

## SIGN_OFFLINE_MESSAGE — INS 0x03

三个指令路由至同一签名处理器。区分它们是为了兼容不同版本的 Solana App；OKX Wallet 主要使用 `INS 0x06`。

**完整 APDU：** `E0 06 P1 P2 Lc [Data]`

### 分帧机制

**P1——帧位置：**

| P1 | 含义 |
|---|---|
| `0x01` | 第一帧（开启新的签名会话） |
| `0x00` | 续帧（若无活跃会话则自动开启新会话） |

**P2——续帧标志位：**

| P2 bit 0 | 含义 |
|---|---|
| `0x01` | 后续还有帧——响应 `9000` 并等待 |
| `0x00` | 这是最后一帧——签名并返回结果 |

### 第一帧数据布局（标准格式）

```
path_count(1)  +  [path_component(4) × path_count]  +  message_bytes...
```

### OKX num_signers 兼容

OKX Wallet 在第一帧的 BIP-32 路径前额外添加一个 `num_signers` 字节（`0x01`）。标准 Ledger 客户端没有此前缀。

**OKX 发送的第一帧数据：**
```
01  02  8000002C  800001F5  ...message_bytes...
│   │   └─ 路径分量 1 ────┘
│   └─ path_count = 2
└─ num_signers = 0x01（OKX 专有前缀）
```

**标准客户端发送的第一帧数据：**
```
02  8000002C  800001F5  ...message_bytes...
│   └─ 路径分量 1 ────┘
└─ path_count = 2
```

**自动检测逻辑：** 处理器通过启发式判断自动剥离该前缀：

```ts
const hasNumSignersPrefix =
  data[0] === 0x01 &&
  data.length > 1 &&
  data[1] >= 2 &&
  data[1] <= 5;

const { path, rest } = parseBip32Path(
  hasNumSignersPrefix ? data.slice(1) : data
);
```

条件 `data[1] in [2..5]` 用于识别合法的 `path_count` 值。由于真正的 `num_signers=0x01` 前缀后面紧跟的总是 `path_count`，这个启发式条件能可靠地区分两种格式。

### 签名逻辑

Ed25519 原始签名——不预哈希：

```
signature(64) = ed25519_sign(message_bytes, privKey)
```

### 响应

**中间帧（P2 bit 0 = `0x01`）：** 仅 `9000`。

**最后一帧（P2 bit 0 = `0x00`）：**
```
signature(64)  +  9000   共 66 字节
```

64 字节签名为原始 Ed25519 签名（R‖S）。钱包 App 在广播前将其嵌入 Solana 交易的线格式中。

## 签名会话生命周期

1. 宿主发送第一帧（`P1 = 0x01` 或无活跃会话时的首帧）：处理器分配签名会话，存储私钥，开始累积消息字节。
2. 宿主发送续帧（`P1 = 0x00`，`P2 = 0x01`）：处理器将字节追加到会话缓冲区，响应 `9000`。
3. 宿主发送最后一帧（`P2 = 0x00`）：处理器调用 `signRequestHandler` 等待用户确认，批准后返回签名，拒绝则返回 `6985`。
4. 无论结果如何，会话均被清除。

**签名会话超时：** 自第一帧起 120 秒。若用户未在超时前响应，处理器自动以 `6985` resolve。

---

## 路径要求

所有 SLIP-10 Ed25519 派生路径必须使用完全硬化的分量。常用路径：

| 用途 | 路径 |
|---|---|
| 主账户 | `m/44'/501'/0'/0'` |
| 第二账户 | `m/44'/501'/1'/0'` |
| OKX 默认 | `m/44'/501'/0'` |

非硬化路径分量与 Ed25519 私钥派生不兼容，会静默地产生错误密钥——没有任何报错提示。
