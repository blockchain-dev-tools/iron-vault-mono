# Key Derivation

IRON Vault derives private keys from a single BIP-39 mnemonic phrase. Ethereum accounts use BIP-32 HD key derivation; Solana accounts use SLIP-10 with Ed25519 — a distinct algorithm that is incompatible with BIP-32.

All derivation logic lives in `packages/crypto/src/`.

---

## Mnemonic Generation and Validation

**Source:** `packages/crypto/src/mnemonic.ts`
**Library:** `@scure/bip39` with the English wordlist

```ts
import { generateMnemonic, validateMnemonic, mnemonicToSeed } from '@iron-vault/crypto';

// 12 words (128 bits of entropy)
const phrase12 = generateMnemonic(128);

// 24 words (256 bits of entropy)
const phrase24 = generateMnemonic(256);

// Validate a user-supplied phrase
const isValid = validateMnemonic(phrase); // boolean

// Convert to seed (async, PBKDF2-SHA512, 2048 rounds)
const seed: Uint8Array = await mnemonicToSeed(phrase);          // 64 bytes
const seedWithPassphrase = await mnemonicToSeed(phrase, 'opt'); // BIP-39 passphrase
```

| Function | Input | Output |
|---|---|---|
| `generateMnemonic(128)` | — | 12-word phrase |
| `generateMnemonic(256)` | — | 24-word phrase |
| `validateMnemonic(phrase)` | string | boolean |
| `mnemonicToSeed(phrase, passphrase?)` | string, string? | `Uint8Array(64)` |

`mnemonicToSeed` is asynchronous because the underlying PBKDF2-SHA512 computation is intentionally slow. The optional `passphrase` argument defaults to an empty string.

## Ethereum Key Derivation (BIP-32)

**Source:** `packages/crypto/src/hdkey.ts` — `deriveEthPrivateKey`
**Library:** `@scure/bip32`

Ethereum uses the standard BIP-32 HD key tree with a BIP-44 coin type of `60`.

```ts
import { HDKey } from '@scure/bip32';

function deriveEthPrivateKey(seed: Uint8Array, pathComponents: number[]): Uint8Array {
  const root = HDKey.fromMasterSeed(seed);
  const child = root.derive(bip32PathToString(pathComponents));
  if (!child.privateKey) throw new Error('No private key derived');
  return child.privateKey; // 32 bytes
}
```

### Standard derivation path

```
m / 44' / 60' / 0' / 0 / index
```

| Segment | Value | Meaning |
|---|---|---|
| `44'` | `0x80000000 \| 44` | BIP-44 purpose |
| `60'` | `0x80000000 \| 60` | Ethereum coin type |
| `0'` | `0x80000000 \| 0` | Account 0 |
| `0` | `0` | External chain |
| `index` | `0, 1, 2, …` | Address index |

Hardened path components are encoded by ORing the index with `0x80000000`. For example, `44'` is stored as `0x8000002C`.

The call sequence for the first Ethereum address:

```ts
const seed = await mnemonicToSeed(phrase);
const pathComponents = [0x8000002C, 0x8000003C, 0x80000000, 0, 0];
const privKey = deriveEthPrivateKey(seed, pathComponents); // 32-byte Uint8Array
```

## Solana Key Derivation (SLIP-10 Ed25519)

**Source:** `packages/crypto/src/hdkey.ts` — `deriveSolanaPrivateKey`
**Libraries:** `@noble/hashes/hmac`, `@noble/hashes/sha2`

Solana uses Ed25519 keys. BIP-32 is not defined for Ed25519, so IRON Vault implements **SLIP-10** instead. The derivation algorithm is fundamentally different from BIP-32.

> **Critical:** Every component of a SLIP-10 Ed25519 path **must** be hardened. The function throws `Error('SLIP-10 Ed25519 requires all-hardened paths')` if any unhardened component is passed.

### Master key derivation

```
I = HMAC-SHA512(key = "ed25519 seed", data = seed)
kL = I[0..31]   // left 32 bytes — master private key
kR = I[32..63]  // right 32 bytes — master chain code
```

The HMAC key is the ASCII string `"ed25519 seed"` (12 bytes), not a raw byte value.

### Child key derivation (per path component)

For each hardened path component `index` (with MSB already set):

```
data = 0x00 || kL || index_BE32

I_child = HMAC-SHA512(key = kR, data = data)

kL_child = I_child[0..31]
kR_child = I_child[32..63]
```

Where `index_BE32` is the 32-bit big-endian encoding of the full component value (MSB included). The `0x00` prefix byte and the use of `kR` as the HMAC key distinguish this from BIP-32 normal child derivation.

### Standard derivation path

```
m / 44' / 501' / account' / 0'
```

| Segment | Value | Meaning |
|---|---|---|
| `44'` | `0x80000000 \| 44` | BIP-44 purpose |
| `501'` | `0x80000000 \| 501` | Solana coin type |
| `account'` | `0x80000000 \| n` | Account index |
| `0'` | `0x80000000 \| 0` | Hardened change level |

The function returns the final `kL` value (32 bytes), which is the Ed25519 private key scalar.

```ts
const seed = await mnemonicToSeed(phrase);
const pathComponents = [0x8000002C, 0x800001F5, 0x80000000, 0x80000000];
const privKey = deriveSolanaPrivateKey(seed, pathComponents); // 32-byte Uint8Array
```

## Address Derivation

**Source:** `packages/crypto/src/signer.ts` and `packages/crypto/src/address.ts`

### Ethereum address

```ts
function ethPubKeyToAddress(privKey: Uint8Array): { pubKey: Uint8Array; address: string }
```

1. Derive uncompressed secp256k1 public key: 65 bytes (`04 || X || Y`)
2. Strip the `04` prefix, leaving 64 bytes (`X || Y`)
3. `hash = keccak256(pubKey[1:])` — 32 bytes
4. `raw = hash[12:]` — last 20 bytes, hex-encoded lowercase
5. Apply EIP-55 mixed-case checksum

The returned `address` string does not include the `0x` prefix. Callers prepend it:

```ts
const { address } = ethPubKeyToAddress(privKey);
const full = '0x' + address; // e.g. "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045"
```

### Solana address

```ts
function solanaPubKey(privKey: Uint8Array): Uint8Array // 32 bytes
```

1. Compute Ed25519 public key: `ed25519.getPublicKey(privKey)` → 32 bytes
2. Base58-encode the 32-byte public key

```ts
import { base58 } from '@scure/base';
const pubBytes = solanaPubKey(privKey);
const full = base58.encode(pubBytes); // e.g. "7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU"
```

## High-Level Helper: `deriveAccountsFromPaths`

**Source:** `packages/crypto/src/address.ts`

This is the primary API for deriving multiple accounts at once.

```ts
async function deriveAccountsFromPaths(
  mnemonic: string,
  ethPaths: string[],
  solPaths: string[],
  passphrase?: string,
): Promise<WalletAccounts>
```

```ts
interface Account {
  full: string;   // full address string (with 0x prefix for ETH)
  short: string;  // first 6 chars + "..." + last 5 chars
  path: string;   // derivation path string, e.g. "m/44'/60'/0'/0/0"
}

interface WalletAccounts {
  eth: Account[];
  sol: Account[];
}
```

Example usage:

```ts
const accounts = await deriveAccountsFromPaths(
  mnemonic,
  ["m/44'/60'/0'/0/0", "m/44'/60'/0'/0/1"],
  ["m/44'/501'/0'/0'", "m/44'/501'/1'/0'"],
);

accounts.eth[0].full;   // "0xd8dA6BF26964aF9D7..."
accounts.eth[0].short;  // "0xd8dA...96045"
accounts.eth[0].path;   // "m/44'/60'/0'/0/0"
```

> **Deprecated:** `deriveWalletAccounts(mnemonic, ethCount, solCount)` is kept for backward compatibility but generates sequential paths internally. Prefer `deriveAccountsFromPaths` for all new code.

## Key Derivation Summary

| Chain | Algorithm | Path | Returns |
|---|---|---|---|
| Ethereum | BIP-32 (`@scure/bip32`) | `m/44'/60'/0'/0/{i}` | 32-byte secp256k1 private key |
| Solana | SLIP-10 Ed25519 (`@noble/hashes`) | `m/44'/501'/{i}'/0'` | 32-byte Ed25519 private key scalar |

The two algorithms share the same mnemonic and seed but diverge completely after `mnemonicToSeed`. They must not be mixed — passing a Solana private key to an Ethereum signing function (or vice versa) will silently produce invalid signatures.
