# Signing Formats

IRON Vault implements four signing operations across two chains. All signing logic lives in `packages/crypto/src/signer.ts`.

Every function returns a raw byte array, not a hex string. The APDU layer is responsible for encoding the response into a Ledger reply frame.

---

## Output Format

All Ethereum signing functions return a 65-byte buffer with the layout:

```
[ v (1 byte) | r (32 bytes) | s (32 bytes) ]
```

The `v` value encodes the recovery bit and, for legacy transactions, the chain ID. Its precise value depends on the signing method — see the table in each section below.

Solana signing returns a 64-byte raw Ed25519 signature with no additional framing.

---

## ETH: Transaction Signing

**Function:** `signEthTransaction(privKey, rlp)`

```ts
function signEthTransaction(privKey: Uint8Array, rlp: Uint8Array): Uint8Array
// Returns: v(1B) + r(32B) + s(32B) = 65 bytes
```

### Algorithm

```
hash = keccak256(rlp)
sig  = secp256k1.sign(hash, privKey, { lowS: true })
```

The input `rlp` is the complete raw transaction bytes as presented by the host app — including the type-prefix byte for EIP-2718 typed transactions. The hash is computed over the entire byte sequence in a single pass; there is no double-hashing.

Low-S normalization (`lowS: true`) ensures the `s` component is always in the lower half of the curve order, which is required by EIP-2 and expected by all modern Ethereum clients.

### v-value calculation

The `v` value differs by transaction type. IRON Vault distinguishes typed transactions from legacy ones by inspecting the first byte of `rlp`:

| TX type | Detection | `v` value |
|---|---|---|
| EIP-1559 (type 2) | `rlp[0] === 0x02` | recovery bit (0 or 1) |
| EIP-2930 (type 1) | `rlp[0] === 0x01` | recovery bit (0 or 1) |
| Legacy EIP-155 | `rlp[0] > 0x7F` | `37 + recovery` (chain ID = 1) |

In code, this is a single condition:

```ts
const isTyped = rlp[0] <= 0x7f;
const v = isTyped ? recoveryBit : 37 + recoveryBit;
```

EIP-2718 typed transactions (type 1 and type 2) encode the chain ID directly inside the RLP payload, so `v` carries only the recovery bit. Legacy EIP-155 transactions encode the chain ID in `v` using the formula `v = 2 * chainId + 35 + recovery`; with `chainId = 1` this simplifies to `37 + recovery`.

> **Note:** The chain ID is currently hardcoded to `1` (Ethereum mainnet) for legacy transactions. Typed transactions are unaffected because they embed the chain ID in their RLP.

## ETH: Personal Message Signing

**Function:** `signEthPersonalMessage(privKey, message)`

```ts
function signEthPersonalMessage(privKey: Uint8Array, message: Uint8Array): Uint8Array
// Returns: v(1B) + r(32B) + s(32B) = 65 bytes
```

### Algorithm

Implements [EIP-191](https://eips.ethereum.org/EIPS/eip-191) `personal_sign`:

```
prefix  = "\x19Ethereum Signed Message:\n" + len(message)
payload = prefix || message
hash    = keccak256(payload)
```

The `len` is the decimal string representation of `message.length` in bytes — not a hex value, not a padded integer.

```ts
const prefix = new TextEncoder().encode(
  `\x19Ethereum Signed Message:\n${message.length}`
);
```

### v-value

```
v = 27 + recovery
```

`personal_sign` always uses `27` or `28` for `v`, regardless of chain ID. This is historical convention predating EIP-155 and is what all Ethereum wallets and dApps expect for this signing method.

## ETH: EIP-712 Typed Data Signing

**Function:** `signEthEip712(privKey, domainHash, structHash)`

```ts
function signEthEip712(
  privKey: Uint8Array,
  domainHash: Uint8Array,  // 32 bytes
  structHash: Uint8Array,  // 32 bytes
): Uint8Array
// Returns: v(1B) + r(32B) + s(32B) = 65 bytes
```

### Algorithm

Implements [EIP-712](https://eips.ethereum.org/EIPS/eip-712) hash-only mode:

```
payload = 0x19 || 0x01 || domainHash(32B) || structHash(32B)
          = 66 bytes total
hash    = keccak256(payload)
```

```ts
const payload = new Uint8Array(2 + 32 + 32);
payload[0] = 0x19;
payload[1] = 0x01;
payload.set(domainHash, 2);
payload.set(structHash, 34);
const hash = keccak_256(payload);
```

The two-byte prefix `\x19\x01` is the EIP-712 version specifier. The function operates in **hash-only mode**: it does not compute `domainHash` or `structHash` itself. The host app (OKX Wallet, MetaMask) must compute both hashes from the typed data structure and pass the 32-byte values directly to this function via the APDU payload.

### v-value

```
v = 27 + recovery
```

Same as `personal_sign` — always `27` or `28`.

## SOL: Message Signing

**Function:** `signSolanaMessage(privKey, message)`

```ts
function signSolanaMessage(privKey: Uint8Array, message: Uint8Array): Uint8Array
// Returns: 64-byte raw Ed25519 signature
```

### Algorithm

```ts
return ed25519.sign(message, privKey);
```

Solana signing is a direct Ed25519 signing operation with no prefix and no pre-hashing. The Ed25519 algorithm internally applies SHA-512 as part of the signature computation (per RFC 8032), but this is opaque to the caller.

The `message` parameter is a serialized Solana transaction message as produced by the Solana SDK — typically a `VersionedTransaction` or legacy `Transaction` serialized to bytes. No additional framing is applied.

The output is a 64-byte signature in `(R, S)` format as defined by Ed25519. There is no `v` byte.

---

## Comparison Table

| Method | Input | Hash construction | `v` value | Output size |
|---|---|---|---|---|
| `signEthTransaction` | RLP bytes | `keccak256(rlp)` | `0/1` (typed) or `37/38` (legacy) | 65 bytes |
| `signEthPersonalMessage` | raw message | `keccak256("\x19Ethereum…\n{len}" \|\| msg)` | `27/28` | 65 bytes |
| `signEthEip712` | domainHash + structHash | `keccak256("\x19\x01" \|\| domain \|\| struct)` | `27/28` | 65 bytes |
| `signSolanaMessage` | serialized tx | none (Ed25519 internal SHA-512) | none | 64 bytes |

---

## Low-S Normalization

All three Ethereum signing functions pass `{ lowS: true }` to `secp256k1.sign`. This instructs the `@noble/curves` library to negate `s` if it falls in the upper half of the secp256k1 order (`s > n/2`), producing an equivalent signature with a lower `s` value.

Low-S signatures are required by EIP-2 and enforced by Ethereum clients since Homestead. Without this flag, some signatures would be rejected by `ecrecover` on-chain.

---

## Error Handling

None of the signing functions validate the private key length or format. Passing a key that is not 32 bytes will produce undefined behavior from the underlying `@noble/curves` primitives. Key validation is the responsibility of the derivation layer (`deriveEthPrivateKey`, `deriveSolanaPrivateKey`), which always returns exactly 32 bytes.
